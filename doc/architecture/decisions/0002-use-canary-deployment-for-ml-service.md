# 2. use-canary-deployment-for-ml-service

Date: 2026-05-11

## Status

Accepted

## Context

В проекте реализуется ML-сервис, для которого требуется безопасное 
обновление версии модели. При выпуске новой версии существует риск технической 
ошибки в endpoint `/predict`, некорректного ответа endpoint `/health`, 
несовместимости зависимостей или ухудшения качества предсказаний.

Дополнительное ограничение состоит в том, что в текущей реализации 
сервиса отсутствует полноценная обработка ошибок. Поэтому прямое переключение 
всего трафика на новую версию модели является рискованным, так как 
ошибка в новой версии может сразу повлиять на всех пользователей.

Были рассмотрены две основные стратегии развертывания.

Первая альтернатива — Blue-Green Deployment. В этой стратегии поддерживаются 
два окружения: `blue` со стабильной версией и `green` с новой версией. 
После проверки новой версии весь трафик переключается с `blue` на `green`. 
Преимущество стратегии состоит в простом rollback, то есть при ошибке можно 
быстро вернуть трафик на старое окружение. Недостаток состоит в том, 
что переключение обычно происходит сразу для всего трафика. 
Если ошибка не была обнаружена на этапе предварительной проверки, она может 
затронуть всех пользователей одновременно.

Вторая альтернатива — Canary Deployment. В этой стратегии новая версия получает 
только часть трафика. Например, сначала 90% запросов направляются на стабильную 
версию `v1.0.0`, а 10% на новую версию `v1.1.0`. Если новая версия проходит 
проверки `/health`, `/predict` и не показывает ошибок в логах, её долю можно 
постепенно увеличить до 50%, а там уже до 100%. При ошибках трафик возвращается 
на стабильную версию.

## Decision

Для данного проекта выбрана стратегия Canary Deployment.

Стабильная версия ML-сервиса `v1.0.0` продолжает обрабатывать основную часть 
запросов, а новая версия `v1.1.0` сначала получает только ограниченную долю трафика. 
Начальное распределение трафика задается как 90/10: 90% запросов направляется 
на `v1.0.0`, 10% запросов направляется на `v1.1.0`.

После успешной проверки endpoint `/health`, endpoint `/predict`, логов и базовых 
технических метрик доля новой версии может быть увеличена. В этой реализации 
предполагаются три режима:

- 90/10 для первичной проверки новой версии;
- 50/50 для промежуточной проверки;
- 0/100 для полного переключения на новую версию.

Если новая версия работает некорректно, выполняется rollback - весь трафик 
возвращается на стабильную версию `v1.0.0`.

## Consequences

Положительные последствия выбранного решения:

- снижается риск массового отказа сервиса при выпуске новой версии модели;
- новая версия проверяется постепенно, а не сразу на всем трафике;
- появляется возможность быстро вернуть трафик на стабильную версию `v1.0.0`;
- можно анализировать логи и метрики новой версии перед полным переключением;
- стратегия хорошо подходит для ML-сервиса, так как ошибка может быть связана 
не только с падением приложения, но и с ухудшением качества предсказаний.

Отрицательные последствия и риски:

- реализация Canary Deployment сложнее, чем простое Blue-Green переключение;
- требуется балансировщик, который умеет распределять трафик между версиями;
- нужно одновременно поддерживать две версии сервиса;
- без дополнительного мониторинга качества модели Canary проверяет в основном 
техническую стабильность, а не полную бизнес-эффективность модели;
- при малом объеме трафика 10% запросов могут быть недостаточны для 
статистически надежной оценки качества новой модели.

Для снижения этих рисков в проекте используются healthcheck endpoint `/health`, 
тестовый endpoint `/predict`, логи контейнеров и возможность rollback на стабильную версию.
